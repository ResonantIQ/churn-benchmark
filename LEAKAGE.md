# Leakage Hygiene

A held-out benchmark only works if the labels aren't recoverable from the
input. The internal harness enforces this with a leakage guard: a denylist
of event types, snapshot fields, and transcript phrasings that would let a
model (or a human) read off the label instead of predicting it. This pack
ships only what passed that guard.

## Data provenance

The corpus is entirely synthetic, generated by Resonant IQ's internal
simulation harness ([ResonantForge](https://github.com/ResonantIQ/resonantforge)), not real customer data. It models 200
SaaS accounts over a 6-month simulated window: support conversations across
multiple channels, billing/lifecycle events, and account behavior, with a
mix of healthy and declining accounts planted by the generator. Labels are
the account's realized outcome after day 90 (churned / retained), derived
from the generator's ground truth, never guessed or inferred from the same
data the model sees.

- `data/conversations.jsonl`: 3,071 synthetic support conversations across
  200 accounts, pre-scrubbed at rest (see **Transcript scrubbing and ID
  handling** below).
- `data/events.jsonl`: 10,691 observable lifecycle/billing/support events
  (account creation, payments, tickets, renewals-approaching, conversation
  start/end), pre-filtered (see **What was stripped, and why**).
- `labels/labels-t90.json`: held-out outcome labels for all 200 accounts at
  the T90 cutoff: 32 churned, 146 retained, 22 excluded (no post-cutoff
  observation horizon, or outcome already resolved before the cutoff; these
  aren't guessable either way, so they're excluded from scoring rather than
  scored as a coin flip).

## Pre-cutoff filtering

Both data files are filtered to the T90 observation window before
publishing. Nothing after day 90 is included: every event with
`day_index > 90` is removed from `data/events.jsonl`, and every
conversation whose trigger event falls after day 90 is removed from
`data/conversations.jsonl`. `run-benchmark.mjs` already filters to the same
cutoff at prompt-build time, so this doesn't change what the model sees; it
means there's no post-cutoff data sitting in the files at rest to
accidentally read or leak into other tooling.

## What was stripped, and why

- **Events.** The raw corpus events file contains generator annotation
  events that directly encode or precede the outcome: `churn_signal_detected`,
  `escalation_detected`, `renewal_lapsed`, `renewal_completed`,
  `score_correction`, `coaching_note_issued`. These are stripped from
  `data/events.jsonl`. Only observable events survive: account creation,
  payments (received/failed), support tickets (opened/resolved),
  renewal-approaching notices, and conversation start/end markers.
- **Labels.** `labels/labels-t90.json` has only `{account_id, outcome,
  churned}`: no `reason`, no `evidence`, no `churnDay`. Those fields exist
  in the internal label extractor but were dropped here because they leak
  exact timing.
- **Internal-state snapshots.** Not shipped at all: no `snapshots.jsonl`
  (health score/state, lifecycle stage: the actual label source), no
  `activity_events.jsonl`, `contacts.jsonl`, or any of the generator's
  internal bookkeeping (eval expectations, scenario plans, planted-theme
  directives, corrections, disagreements, caches). This pack ships only the
  two data files an arm is contractually allowed to see, plus the held-out
  labels for scoring.

## Transcript scrubbing and ID handling

`data/conversations.jsonl` as shipped has already had the internal
harness's sentence-level redaction applied directly to every transcript's
`prose` field: any sentence narrating internal health/engagement/lifecycle
state ("your health score has been trending downward...") is replaced with
`[redacted: internal account status]`. The file is safe to open and read
directly.

Synthetic account IDs (`acct_001`, etc.) are **not** redacted from
transcript prose, intentionally: these are synthetic IDs, not information
about the outcome. They appear both as metadata join keys in the data files
(`account_id` fields grouping events and conversations) and occasionally
inside prose (e.g. `Customer_acct_001`), identically to how they appeared
in the study's prompts.

`run-benchmark.mjs` re-applies the exact same scrubber to every transcript
before building a prompt. Because the redaction is idempotent (scrubbing an
already-scrubbed sentence is a no-op), this produces byte-for-byte
identical prompts whether the runner reads the pre-scrubbed shipped file or
a hypothetical raw one. We verified this directly: prompts dumped
(`--dump-prompt`) for representative accounts from the raw
pre-publication corpus and from the shipped pre-scrubbed file are SHA-256
identical. The runner also re-asserts, via a ported leakage regex, that no
forbidden phrasing survives in the final prompt before it's sent to the
model, the same check the internal harness runs, now confirming a
guarantee the file already provides rather than being the only enforcement.

If you write your own tooling against this corpus instead of using
`run-benchmark.mjs`, you can read `data/conversations.jsonl` directly (the
redaction is already baked in). If you regenerate or replace it from a raw
source, route transcripts through the scrubber (ported at the top of
`run-benchmark.mjs`) first, or you'll be handing a model (or a human
reader) the answer key.

## Independent verification

We ran an independent leakage sweep on this pack before publishing
(grepping data and label files for lifecycle/renewal/archetype/planted/
scenario/health-state terms); see the pack's build notes to re-run it
yourself. Three independent adversarial reviews caught real leaks in the
corpus this pack was built from before it shipped.
